## 旅程图 vs 故事地图

| | 用户故事地图（hgyjy-user-story） | 用户旅程图（本 skill） |
|---|---|---|
| 回答的问题 | 做什么功能、按什么版本交付 | 用户怎么经历、在哪里受挫、机会在哪 |
| 骨架 | 用户旅程步骤（方案分解） | 时间线上的阶段 |
| 单元 | 功能特性（Who/What/When/Why/DoD） | 阶段×七维度（行动/触点/想法/情绪/痛点/机会点） |
| 产出用途 | 需求拆解、版本规划、排期 | 体验诊断、机会发现、假设验证清单 |
| 数据文件 | story_map.json | journey_map.json |

两者互补：旅程图发现的"机会点"成熟后，可以转成故事地图里的功能特性。不要在一张图里同时干两件事。

## 定范围：一张图一个角色一段场景

旅程图的横向轴是**时间**，时间是单线程的。一张图里塞多个角色或多个互不相关的目标，阶段会互相打架。

- 同一角色、同一情境、换一个目标 → 另起一张图（如"工艺工程师查故障"与"工艺工程师归档案例"）。
- 角色描述要具体到能想象出这个人："LPBF 工艺工程师，3 年设备调试经验，熟悉工艺参数但不熟悉新机型"，而不是"用户"。
- 场景要包含**时间压力/约束**："新机型首件打印出现球化缺陷，需要在 2 小时内定位原因"比"使用知识库"有效得多——时间压力决定情绪，情绪决定痛点权重。

## 七维度填写指引

每阶段按固定顺序过一遍：

| 维度 | 写什么 | 提问话术 | 常见错 |
|------|--------|---------|--------|
| 目标 | 用户在这个阶段想达成什么 | "走到这一步，他想完成什么？" | 写成系统功能（"系统要支持…"） |
| 用户行动 | 用户实际做了什么，动词开头 | "他具体做了什么动作？" | 写成系统行为；一步塞多个动作 |
| 触点 | 通过什么渠道/界面/人 | "他是通过什么接触到系统的？屏幕、口头、文档？" | 漏掉线下触点（同事口头推荐） |
| 想法/疑问 | 用户内心独白，原话式 | "这时候他脑子里在想什么？用他自己的话说" | 写成设计者的判断（"他觉得界面不友好"） |
| 情绪 | -2..2 五档或留空 | "这时候心情怎么样？非常糟/有点糟/一般/不错/很好" | 为填满而编；把结果情绪当过程情绪 |
| 痛点 | 什么让目标变难 | "哪一步让他卡住了/烦了？" | 与机会点混淆；写解决方案而非问题 |
| 机会点 | 解决痛点后世界变成什么样 | "如果这个问题消失了，体验会怎样？" | 写成具体功能方案（那是下一步的事） |

挖掘纪律：**每个痛点至少追一句"如果解决了会怎样"得到一个机会点**；每个低谷情绪（≤-1）阶段，回看该阶段痛点是否抓全。

## 事实/假设分标纪律

旅程图是**综合分析产物，不是头脑风暴记录**。填每条内容时问一句："这个我们是怎么知道的？"

- **事实（fact）**：来自用户访谈、行为数据、客服工单、现场观察。能说出出处的才算。
- **假设（hypothesis）**：团队推测、拍脑袋、从别的产品类比来的。一律标假设。

为什么强制：一张全是假设的旅程图会给人"已经研究过了"的错觉，直接拿去排需求就是把赌注当结论。图上橙色列就是给用户看的"待验证清单"——建议产品团队按假设阶段的痛点优先级安排验证（访谈、埋点、可用性测试）。

实操：默认先标假设；只有当用户明确说出处（"我们访谈过 5 个工艺工程师""工单数据显示…"）才标事实。

## 情绪评分

五档：2 非常积极 / 1 积极 / 0 中性 / -1 消极 / -2 非常消极。

- 评分看**相对变化**而不是绝对水平：多数日常任务在 0 到 1 之间波动，真正的信号是骤降段。
- 拿不准就留空（未评估），曲线在该阶段断开——空白本身也是信息（"这段我们不了解"）。
- 情绪必须能指回一个具体原因："消极，因为答案没有出处无法判断可信度"，不接受无因情绪。

## 关键时刻（Moments of Truth）

关键时刻 = 用户形成"这东西靠不靠谱/值不值得用"判断的那个瞬间，通常在：信任建立（第一次得到靠谱答案）、信任崩塌（发现系统胡说）、或价值兑现（任务真正完成）处。

- 一张图提炼 2–4 个，用 `add_moment` 记录为完整句子。
- 检验标准：如果这个瞬间体验崩了，用户会不会流失？会 → 是关键时刻；不会 → 只是普通痛点。

## 常见错误表

| 错误 | 症状 | 纠正 |
|------|------|------|
| 一张图多个角色 | 阶段里出现"用户/管理员/领导"混着来 | 拆图 |
| 阶段写成系统流程 | 阶段名是"登录/查询/返回结果" | 换成用户的概念："认知/首次提问/验证答案" |
| 行动写成系统行为 | "系统检索知识库并返回答案" | 改成用户动作："他把缺陷照片和参数发给智能体" |
| 痛点=解决方案 | "缺少导出按钮" | 退回问题："他要把答案带给谁看，现在怎么办？" |
| 全程情绪 1-2 | 曲线平在上方 | 追问低谷："哪一步他最没底？" |
| 假设不标注 | 图上看不出哪些待验证 | 逐阶段过 evidence |
| 阶段超过 7 个 | 图又细又长 | 拆场景，或合并中间阶段 |
